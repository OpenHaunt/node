# 16 — A standalone show

**Status: designed on 2026-10-29, not built.** Nothing in the firmware below exists yet.

A prop that used to run on an OctoBanger has a trigger, an ambient loop, a scare, and a cold period
after it, and it ran with nothing else in the room. The same prop on an OpenHaunt node needs a
console today: an input goes out on MQTT and only the console decides what happens. This doc
describes how a console puts **one flow and its timelines** onto a node, so that the node runs them
on its own.

Like docs 13–15, this is an extension to doc 08. A node without it works as before, and a console
that never deploys a show never sees it.

The console side is the-pult, `docs/ROADMAP.md`, entry *standalone-node-show*. Its OctoBanger
import (task 97) already turns a prop into exactly this shape: a scare timeline, an ambient timeline
that loops, and a flow that plays the scare on the input's edge.

## What was decided

- **Standalone, not a fallback.** A node is either driven by a console or runs its deployed show.
  It does not switch over by itself when the console goes away. Doc 08's *Standalone operation*
  imagines an escape room whose server crashed. That is not this, and it stays unbuilt.
- **One node, alone.** No node starts anything on another. A scare across several props stays the
  console's job.
- **Authored only on the console.** The node receives a finished package and does not edit it. Its
  web page shows what is loaded, presses the flow's buttons, and sets one master volume.
- **A strict subset.** The console refuses to export anything a lone node can't run: sequences and
  cues, fixtures on other nodes or on DMX, the speed master. It names each one. Nothing is dropped
  silently.
- **The flow graph runs on the node**, not a fixed OctoBanger program.
- **The firmware targets the S3 for V0**, in `oh_core`, so it can move to the RP2354 later or stay.
- **This reverses the Heinz Horror Garten's decision 16**, "the nodes stay plain I/O with no local
  rules", for a node in standalone mode, and only there.

## The package

One show per node. It is stored as a file on the `clips` FAT, beside the clips it plays, and counts
against the same budget (`bytes_free`). There is no new partition: a partition change needs a USB
flash of every node (`firmware/README.md`), and the show file is small next to its sound.

- **A manifest**, JSON, which `oh_core` already reads with cJSON:
  - format version, show hash, export time, the console's name for it
  - variables: id, flag or number, initial, min, max
  - the flow: nodes and edges, in the console's own vocabulary (below)
  - timelines (at most **4**): length, end (`stop` or `loop` at a time), events, clips
  - clips: sha256, start, offset, length, gain, fades, repeats, and the voice routing for this
    node's speaker (the zone's level and sides, already applied by the console)
- **Tracks in a compact binary** beside it, one per (timeline, port): change points `(ms, value)`,
  played back stepwise. A three-minute fader recording as JSON would be thousands of cJSON objects
  in 2 MB of PSRAM, which is why tracks are not in the manifest.
- **The show hash** identifies what the package was built from. The console compares it with its
  own show to say *out of date*. It never redeploys on its own: the prop may be in front of guests.

Everything the package refers to has already been resolved by the console. A track names a **port
on this node**, never a fixture. A clip names a **sha already in the store**. The node never sees a
zone, a fixture type, or another node.

## The flow on the node

The interpreter is a port of the-pult's `model/flows.rs` to C in `oh_core`. It is pure and
host-tested, the way `oh_effect` and `oh_pixfx` are. These are the console's node kinds, restricted
to what the export allows:

| Kind | On the node |
|---|---|
| `Started` | **New.** One pulse when the flow starts: at boot here, when the flow is enabled on the console |
| `Source` | A port of this node (a PIR is a `contact` input) or a variable |
| `Button` | Pressed from the node's web page |
| `Condition` | Rising, falling, any change, above, below |
| `And`, `Or`, `Not`, `Gate` | As on the console |
| `Delay` | Start/restart on port 0, reset on port 1 |
| `Action` | `PlayTimeline` (ignore/restart if running), `StopTimeline`, `SetVariable`, `SetParameter` on a port of this node |

The semantics have to match the console's exactly, including that a write is not seen inside the
pass that made it, that several wires into one input act as an OR, and that a feedback chain is cut
after 16 passes. **Both implementations run the same test cases from one file**, generated by the
console, as `14-pixel-effects.json` does for pixel effects.

**An arming delay is part of the flow**, not a package setting: `Started` → `Delay 30 s` → set
`armed`, and the input's edges pass a `Gate` on `armed`. A PIR that fires while it settles after
power-on is ignored. The OctoBanger import turns `boot_delay_s` into this.

**Variables start at their initial value on every boot** and are never written to flash while a
show runs. That matches an OctoBanger, and doc 01's "deterministic reset behavior".

## Timelines on the node

- **Time is the node's own** monotonic clock. With no console there is no `openhaunt/clock` to
  follow, and none is needed: every time in a package is relative to a timeline's start.
- **Tracks** are sampled on the render tick (25 ms, `oh_render`) and written through the port layer,
  the same path a `set` takes today.
- **Clips** start on the mixer (doc 13) at their position. A timeline stopped or cut short stops its
  voices.
- **Events** at a position play or stop a timeline or set a variable. They are the flow's actions,
  the way the console does it (`as_flow_action`).
- **The end** stops the timeline or loops it. The OctoBanger lockout is "the scare is still
  running", with `PlayTimeline` set to ignore a running timeline, so no variable is needed for it.

## The mode

- **Entering.** The console uploads the clips, then the package, then switches the node to
  standalone. The flag is kept in NVS, so power-on goes straight back into the show.
- **Deploying onto a running show** stops it first. Clips and package go up with nothing playing,
  because a flash erase during playback can underrun the output (doc 13). The new package is then
  checked and started from `Started`. **A package that fails the check leaves the old one in place,
  and the old one runs.**
- **A package that can't run at boot** (damaged, or a clip it names is missing) is not started. The
  outputs stay at their port defaults, the status LED shows a fault, and the web page and MQTT status
  say what is missing. A prop doing half its show is worse than one that is visibly broken.
- **While standalone**, `output/*` and `audio/*` commands are ignored. Inputs and health are reported
  as usual if a broker is reachable. Standalone state goes with them: which show, which timelines are
  running, the variables, the last trigger.
- **Leaving** stops every timeline and voice, puts every output to its port default, and hands the
  node back to the console. **The package and its clips stay**, so going standalone again with an
  unchanged show uploads nothing.

**A package pins its clips.** The node answers `409` to a `DELETE` of a clip the stored package
names. The console's clip planner counts those clips as wanted, so it does not try to free them.

**The master volume** on the web page is kept across reboots and reset by the next deploy.

## Proposed HTTP

Not settled. This is the shape to start from.

```
PUT    /api/v1/show            the package (manifest + tracks, one archive)
GET    /api/v1/show            what is stored: hash, name, size, check result
DELETE /api/v1/show            remove it (refused while standalone)
POST   /api/v1/show/mode       {"standalone": true|false}
POST   /api/v1/show/press      {"button": "<node id>"}
POST   /api/v1/show/volume     {"gain_db": -6}
```

HTTP rather than MQTT, because a standalone prop may be on a network with no broker, or on none.

## Open

- The package's exact layout: one archive, or a manifest plus track files on the FAT.
- Whether `GET /api/v1/info` announces the capability, so a console knows a node can take a show
  before trying. Doc 06's IO descriptor already has a bit for "stored sequence playback locally".
- Pixel strips: a track can drive an effect parameter port. Whether a strip in standalone mode needs
  anything beyond that has not been looked at.
- On an IO board with an RP2354, whether the interpreter stays on the S3 and sends `SET`s over the
  link, or moves to the RP2354, where the outputs' timing lives.
